01

The shape of it

There is one application. It is a React app that builds into a folder of static files, and that same folder is served three ways: as a website, and as the contents of an Android app and an iOS app. Capacitor is the wrapper that turns the folder into the two native apps — it does not rewrite anything, it just puts the web app inside a native shell and hands it a few native abilities like the camera and vibration.

That app talks to one server over ordinary HTTP requests, plus one long-lived connection used to push alerts down. The server is the only thing that touches the database, and the only thing holding any secret.

02

The pieces

Eleven files on the server, each with one job. The big one is index.js — it holds every route and every rule. The rest are things worth keeping separate because they talk to the outside world or hold a self-contained piece of thinking.

index.js

All 69 routes, sessions, permissions, and the live-alert stream. The rules of the app are here.

db.js

The schema, the connection, and the demo neighbourhood. Speaks to real Postgres or an in-process one for tests.

geo.js

Postcode to coordinates, distance between two points, and the blurring that keeps a pin off a front door.

matching.js

Whether a listing answers a wish — folds plurals and household synonyms, so "bookcase" finds "shelving unit".

address.js

Postcode to a real address. Uses a licensed provider when a key exists, otherwise names the street and asks for the number.

autospec.js

Photograph to product: the name, maker and dimensions, with alternatives to choose from.

moderate.js

Checks a listing before it goes live. Fails open — moderation must never stop a neighbourhood sharing.

ai.js

The small language jobs: understanding a typed sentence, suggesting a reply, translating a message.

weather.js

Asks the sky whether rain is coming, so a doorstep listing can be shortened or postponed.

impact.js

Turns collected items into weight diverted and cost avoided, using published reuse figures.

setup.js

Creates the schema against a fresh database. Run once when pointing at a new Supabase project.

On the client side there are effectively two files: App.jsx holds every screen, and styles.css holds the whole design system. This is unusual and deliberate — one file means no hunting, and the screens share so much state that splitting them would mostly move the complexity into wiring.

A deliberate absence

There is no table of street pages, badges or impact figures. Every one of those is computed when asked, from the tables above. A stored counter drifts the moment anything unusual happens; a number derived on read cannot.

04

Two people, one sofa

The hardest problem in the app is two neighbours tapping Claim on the same sofa in the same second. Both requests arrive; both read a sofa that looks available; without care, both would be told they had it, and one would walk to a stranger's door for nothing.

The fix is a database row lock. The first request to arrive locks that item's row for the length of a short transaction. The second request does not fail — it waits at that line, and when it finally reads the row, the sofa is already claimed, so it gets an honest answer instead of a second promise.

05

How a wish finds you

Someone says they're after a high chair. Later, a neighbour lists one. What happens between those two moments is the app's best feature, and it has four steps.

Step three is subtler than it looks. "Have we told this person already?" is remembered against the person and the item, not the wish. That means deleting a wish and adding it back doesn't replay alerts someone has already read, and two wishes that both match one sofa still produce one alert rather than two.

06

Why the feed is small

Photographs are the heaviest thing in an app like this, and a feed of two hundred listings is where a naive design collapses. Doorstep never sends the same photograph twice.

The tests deserve a note. They don't use mock objects that pretend to be a database — they start the actual server against a real Postgres compiled to run inside Node, exercise the real routes, and throw the database away afterwards. That is why they catch things like the claim race, which a mocked test would sail straight past.

Rules held in code

Some decisions are not features but constraints, enforced in one place so they cannot be forgotten in another.

RuleWhy
Addresses hidden until claimedThe map pin is blurred to roughly a street block for everyone else, and the written address is released to exactly one person for the length of their hold.
Never the pavementLeaving goods on public land is fly-tipping, with fines up to £1,000. Every collection spot offered is on private property.
Banned items refusedMedicines, weapons, car seats, cot mattresses and the rest are refused by a plain word check before any AI is consulted — so the hard bans never depend on a key being configured.
Three households minimumA street page needs three verified homes before it shows any numbers. A page about one household is a page about one person.
Demo data owns upThe demo neighbourhood only seeds a local database, and every seeded listing is labelled, because its addresses are real Hackney streets.
AI is never requiredEvery AI feature answers "nothing" without a key, and the app carries on unchanged. Moderation in particular fails open.

09

What's fragile

An honest architecture document names what will break first.

Alerts don't reach a closed app

The live connection only works while the app is open, and the free server tier sleeps after fifteen minutes and severs it. For an app whose promise is a fast alert on a two-hour window, this is the most consequential gap. Native push is the real fix; email is the cheap one.

Photos live in the database

User photographs are stored as text in Postgres. At roughly 50–150 KB each against a 500 MB allowance, that is a few thousand listings before it hurts. Moving them to file storage and keeping only a link is a day's work, and much easier before there is real data than after.

No backups on the free tier

The database has no snapshot behind it, and the project pauses after seven quiet days. A scheduled dump to somewhere else — and one tested restore — is the cheapest insurance available.

Deliberately not fragile

Lapsed holds, street pages, badges and impact figures are all computed when asked rather than stored, so there is no background job to fail and no counter to drift. That choice costs a little processing and removes a whole category of bug.

Part two

Scaling to a million, without breaking what works

10

The arithmetic first

Before any architecture, the number that decides everything else. A million registered users, at a healthy eight per cent daily active, opening the app three times a day and making ten calls a session, is 2.4 million API calls a day. Spread evenly that is 28 requests a second. Concentrated into the evening peak, call it 140 a second.

The conclusion that shapes everything below

140 requests a second is small. One modest server handles it. Doorstep does not have a throughput problem at a million users — it has three design choices that do not survive a second server. Nothing below is about handling load. It is about removing the three things that make it impossible to run more than one copy of the app.

That is the good news, and it is worth being precise about why: this app is hyperlocal. Nobody ever asks for a national feed. Every query is bounded to a mile or two, so no single request ever needs more than a few dozen rows however many million exist. The workload shards naturally by geography, which is the friendliest possible shape a system can have.

At a million usersFigureVerdict
Peak requests per second~140Comfortable on one server. Trivial across three.
Photo storage per month~24 GBImpossible inside Postgres. Pennies in object storage.
Item rows after five years~12 millionFine with the right index. Fatal without one.
Apps open at peak~10,000Fine across several instances. Impossible on one, as built today.
Alerts fanned out per day~300,000Fine on a worker. Not fine inside the giver's request.

11

The three walls

Everything standing between here and a million users is one of three things, and they arrive in a known order at known sizes.

WallHits atWhat you actually see
1 · Photos inside the database~4,000 listings with photosThe database fills. Writes fail. Everything stops at once.
2 · Alerts held in one process's memoryThe second server instanceHalf your users silently stop getting alerts. Nothing errors.
3 · No index on location~100,000 itemsThe feed gets slower every week until it times out.

Wall two is the important one and the least obvious. It is not a performance problem — it is a correctness problem, and it appears the moment you try to fix any other problem by adding a second server. Until it is gone the whole system is pinned to one machine: no redundancy, no zero-downtime deploys, no scaling out. It is the wall that hides all the others.

Verified against the code, not assumed

The indexes that exist today cover expiry, owner, claimer, notifications, spots and events. There is no index on lat or lng. Separately, every authenticated request costs one extra database round trip to turn a bearer token into a user. Both are cheap to fix and neither announces itself until it is late.

12

The shape at a million

Here is where it needs to arrive. Four things are new: files live outside the database, alerts travel through a shared channel instead of one process's memory, slow work moves off the request, and reads spread across copies. Everything else — the routes, the tables, the app itself — is unchanged.

What stays exactly as it is

Every route, all 25 tables, the claim lock, photos-by-reference, the postcode cache, the tests. Nothing in the first half of this document is redesigned.

What is genuinely new

Object storage with a CDN, a shared publish/subscribe channel, a job queue with workers, native push, a session cache and read replicas — added one at a time, each behind a flag.

13

Wall one · photographs

Today a photograph is stored as text inside the item's own row. It is simple, it works, and it stops working at about four thousand listings. A database is an expensive, transactional, backed-up place to keep bytes that never change and are never queried.

The reference indirection built today — ref:slug resolved through a photo route — is exactly the seam this slides into. The app already asks for a photo by name rather than carrying bytes around, so the change is confined to what that name resolves to.

What it costs

24 GB a month of photographs is a few pounds a month in object storage, and near-nothing in bandwidth once the CDN is caching. The same volume inside a managed Postgres is not purchasable at a sensible price at all. This is the rare change that makes the system both cheaper and faster.

14

Wall two · alerts

This is the wall that decides whether the app can scale at all. When the server wants to alert someone it looks them up in a map held in that process's memory. That is perfect on one server and fails invisibly on two.

The second half of this wall is that a live connection only ever reaches an app that is open. At a million users the answer is native push — Firebase for Android, Apple's service for iOS — with the live connection kept as the instant path for people who happen to be looking. Both read the same stored alert, so there is one source of truth and two delivery routes.

The third half, which is really a throughput point: fanning out a wish match to everyone nearby currently happens inside the giver's own "list it" request. At scale that belongs on a worker, so the giver's screen returns in a moment and the alerts follow a second later.

15

Wall three · finding what is near you

The feed asks one question: which live items sit inside this small box of latitude and longitude? Today there are indexes on expiry, on owner and on claimer — and none on location. With a few hundred items that is invisible. With twelve million rows it is a scan of the whole country on every feed load.

Two smaller wins sit beside it. Every authenticated request currently spends one database round trip turning a token into a user — holding sessions in a cache removes a query from every single call in the system. And the sweep of lapsed holds runs on read, so the busiest moments do the most extra write work; at scale that belongs on a timer.

16

Changing engines mid-flight

The instruction was: do not break things. Every change above can be made with the app running, using the same four steps each time. It is slower than a straight switchover and it is never frightening, because the system works at every step and step three is a flag you can flip back in seconds.

The one rule that keeps it safe

Never do two of these at once, and never take a step on a Friday. Each of the three walls is independent — that is a property worth protecting, because it means any single change can be reversed without unpicking the others.

The latency budget

"Fast" only means something as a number per action. These are the targets worth holding at a million users, and what has to be true for each one.

ActionTargetWhat makes it possible
Feed loadsunder 200 msLocation index, session in cache, 24 items a page, photos by reference.
First cards visibleunder 1 s on 4GSkeletons drawn immediately, images streaming from a nearby edge.
Claim confirmedunder 300 msOne short locked transaction. Cannot be cached, so it must stay small.
Photograph appearsunder 100 msServed from the CDN edge. It never reaches the API twice.
Listing goes liveunder 400 msAI checks moved off the request — the listing appears, the checks follow.
Alert reaches a phoneunder 5 sFan-out on a worker rather than in the giver's request; push for closed apps.
Message deliveredunder 1 sShared channel, so it does not matter which instance either person is on.
The rule behind the whole table

Anything a person is waiting on stays inside the request. Everything else — wish fan-out to thousands of neighbours, AI moderation, digests, sweeps, impact figures — moves to a worker. Today a giver's "list it" request personally waits for the matcher to consider every wish nearby; that is the first thing to move, and it is what keeps the numbers above true as the neighbourhood grows.

18

The order to do it in

Not all at once, and nothing before it is needed. Each step has a trigger — build it when the trigger fires, not sooner. Everything above the line is worth doing before launch; everything below waits for a number.

Do thisTriggerEffort
Index locationNow — it is an afternoon, and it is silent until it isn'tHours
Scheduled backups and one tested restoreBefore the first real userHalf a day
Photographs into object storageBefore real users list at any volume1–2 days
Native push notificationsBefore launch — the product promise depends on it3–5 days
Alerts through a shared channelBefore the second server instance, whenever that comes1–2 days
Sessions in a cache~50k daily activesHalf a day
Queue and workers~50k daily actives, or when listing starts to feel slow2–3 days
Several API instancesOnce alerts are shared — then it is a configuration changeHours

If only three things get done

Index location — an afternoon, and it removes the wall you cannot see coming. Photographs out of the database — the wall you hit first, and far cheaper to move before there is real data than after. Alerts through a shared channel — the wall that silently pins the entire system to one machine, and therefore the one that unlocks everything else.

The rest can wait for its trigger. A million users is 140 requests a second; the architecture on this page is comfortable well past that, and almost none of it needs building today.
